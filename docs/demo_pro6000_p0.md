# Casecade-Demo：PRO 6000 P0 与推理优化验收

完成日期：2026-10-08（北京时间）。实验目录按开始时 UTC 日期命名为 `p0_pro6000_20261007`。所有实验在同一台机器串行进行；原始会话与音频保留在服务器私有实验目录，仓库只保存脚本、自造输入定义和聚合收据。

## 结论

已采用 `setup/start_demo_pro6000.sh`：缩小 KV 预留、收紧 Code2Wav 预热、加载两套 BF16 MoE 参数。原基础配置保持原值。当前三阶段服务和 demo 均健康。

模型自带的 Code2Wav 内部 CUDA Graph 候选完成相同回放与容量测试，但额外消耗约 3GiB 显存，仅观察到约 1.6% RTF 改善，P95 略差，收益不足，未采用。`configs/qwen3_omni_audio_pro6000_graph.yaml` 仅保留为显式实验配置。

系统盘已按用户授权从 200GiB 扩到 250GiB，并在线扩展分区/ext4；文件系统约 242.1GiB，可用 68.9GiB。共享安装缓存清理实际只回收约 1GiB，不能把 36GiB 逻辑缓存大小算作实际回收量；模型、环境与数据均保留。

最终容量检查采样到的显存最小余量为 18.44GiB。与原配置空闲约 2.5GiB 相比，资源余量显著增加，但原配置未同步采样负载峰值，不能把这两项当作严格峰值差值。

## 配置与范围

- NVIDIA RTX PRO 6000 Blackwell Server Edition 96GB；驱动 580.173.02，vLLM 0.22.0，Omni 环境 PyTorch 2.11.0+cu130。
- Thinker：BF16、128 experts、hidden 2048、intermediate 768、top-k 8；Talker：128 experts、hidden 1024、intermediate 384、top-k 6。
- 四个 FCFS 槽位保持；Thinker/Talker 上下文上限仍为 4096/8192。全局 normal=3、total=4，继续为控制判断保留槽位。
- Thinker/Talker 显存占比从 `.72/.16` 改为 `.67/.10`，启动日志对应 KV 容量为 32,352 / 120,880 tokens，分别大于四个完整上下文所需的 16,384 / 32,768 tokens。
- Code2Wav `max_num_batched_tokens/max_model_len` 从 65536/65536 改为 8192/8192；流式 `4:12` + 25 帧左上下文、16 码本，四路典型满块只需 2368 code tokens。该部署配置针对现有 demo 流式路径，不是任意超长离线声码输入配置。
- 最终声码阶段继续 `enforce_eager=true`。图候选设置 `enforce_eager=false` 与 `compilation_config.mode=0,cudagraph_mode=0`，仅启用模型内部图；日志确认 11 个 batch=1 长度桶捕获成功。候选可运行，但没有足够整体收益，因此未成为默认。
- 保持 chelsie/seed42、Talker native numerics、350ms 起播、2s 有界预取、640ms hold、路由/停止/续说/完成性策略。没有更换或量化权重。

## 完整链路与对照

7 个自造语音夹重复使用。每个条件跑中文普通回答、英文普通回答、完整故事、停止后恢复、等待后续说这 5 个场景，各重复 2 次；总计 50 次会话，属于重复工程样本。另有每条件 6 次直接 SSE TTS 探针，其中第二次的三条输入组成表内 warm 统计。

| 条件 | 回放通过 | 首播 P50 秒 | 首播 P95 秒 | warm 首 PCM 中位数 ms | warm RTF 中位数 | 回放最小显存余量 GiB |
|---|---:|---:|---:|---:|---:|---:|
| 原配置 | 10/10 | 1.513 | 1.820 | 237.7 | 0.245 | 未采样；空闲约 2.5 |
| 仅缩小 KV | 10/10 | 1.571 | 1.906 | 239.1 | 0.245 | 4.32 |
| KV + 收紧声码预热 | 10/10 | 1.442 | 1.642 | 272.0 | 0.274 | 18.84 |
| 最终：再加 MoE 参数 | 10/10 | 1.487 | 1.585 | 250.6 | 0.265 | 18.85 |
| 声码图候选（未采用） | 10/10 | 1.462 | 1.623 | 266.4 | 0.260 | 15.86 |

最终相对原配置的观察值：首播 P95 下降 12.9%，warm RTF 增加 7.9%。RTF 为生成耗时/音频时长，越低越好；测量及时消费 SSE，没有浏览器播放背压。生成速度仍约为实时播放的 3.8 倍，但不能宣称整链路吞吐提升。此次主要确定收益是资源余量和部分 MoE 内核性能。

对比同一显存配置，MoE 条件的 warm RTF 中位数从 0.274 变为 0.265，首播 P50 略差、P95 略好，端到端收益较小。每项只有三条 warm 输入/十次回放，数据不足以判断这类几百分点差异是否稳定；没有通过挑样本或修改时序掩盖代价。

所有条件的 50 次会话均闭合 trace，dropped=0；完成回复有非空且非超时的 text_done，结束音频样本数与播放 ACK 覆盖数相符。没有观测到浏览器播放 underrun。最终停止后不主动恢复，续说/恢复均能完成；两次 host-observed 停止延迟为 [523.0, 494.6]ms，这不是物理扬声器停止时间。

## 容量与验收边界

缩小缓存、MoE、最终声码图这三个条件均额外测试四路同时 3508 prompt tokens + 32 output tokens，以及四路同时 TTS，全部成功。容量探针人为将输出限定为 32 tokens，finish_reason=length 是预期容量压力输入，不是完整回复验收。并发结果不拿来作为论文串行延迟，也不代表四个用户的产品并发能力已完成验收。

最终回放采样峰值显存 76.75GiB；四路压力采样峰值 77.15GiB。最终回放系统内存使用峰值（MemTotal-MemAvailable，排除可回收缓存）约 13.77GiB；GPU 温度峰值 46℃、功耗峰值 269.2W。约一秒采样不覆盖更短瞬时尖峰。

70 项现有相关单元测试通过：请求容量/历史预算、页面与启动、传输恢复、长度续写完成性。脚本语法与配置结构检查通过。模型/路由真实运行的证据来自上述服务器回放；测试不能替代真实用户、跨网络或物理声学链路评估，也没有证明跨文本音色、短停召回或一般模型质量零退化。

## 运维与回退

服务器工作目录 `/root/autodl-tmp/fd-badcat`。专用入口在 tmux 中前台运行：

```bash
bash setup/start_demo_pro6000.sh
/root/miniconda3/envs/fd-sds/bin/python scripts/check_demo_resources.py
```

检查器只读：磁盘最低余量 40GiB、GPU 最低余量 4GiB、Omni `:10003` 和 demo `:18000` 健康；异常以非零退出码报告。离线启动前可加 `--allow-stopped`。案例缓存继续使用现有 512MiB/2000 案例/30 天政策，真实原音频默认不采集。

启动器为此机补齐 conda PATH，并限定已验证 MoE JSON 路径。端点仍只监听 127.0.0.1，继续使用已有 SSH 18000 转发。Spot 机器被停止后，需要启动实例并重新执行入口；没有改变 Spot 的停止/计费生命周期。

遇到问题先在所属 tmux 对启动器 Ctrl+C，等待其子进程退出，确认监听端口与 GPU 进程后启动回退。关闭 MoE 仍保留显存/声码优化：

```bash
FDBC_DEMO_MOE_TUNING=0 bash setup/start_demo_pro6000.sh
```

完整回原配置：

```bash
QWEN_DEPLOY_CONFIG="$PWD/configs/qwen3_omni_audio_single_gpu.yaml" \
FDBC_DEMO_MOE_TUNING=0 bash setup/start_demo_pro6000.sh
```

GPU/软件/模型版本改变后重新调优；不要把本机结果当作其他 GPU 的参数。回放 runner 需 backend 环境的 Playwright 1.58.0 与当前 `chromium-1243` 可执行文件。每次选择新输出目录并复用同一组夹；原始输出不提交。

聚合收据：`exp/web_demo/pro6000_p0_20261007_summary.json`；私有逐会话产物：`exp/web_demo/p0_pro6000_20261007/`。下一步产品优化应优先真实设备短停/噪声回归，以及拆分输入确认、推理与起播缓冲的延迟预算；本次不以小样本替代这些验收。
