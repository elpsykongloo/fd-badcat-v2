# Demo 延迟与并发进度改进

本轮对应 P1 延迟拆解后的四项工作：并发进度和首播前控制、计时关联与起播缓冲、实质首个 TTS 单元、分类尾部与第二轮调度。改动只由独立 demo 配置显式启用。HumDial 基线、冻结评测和 TACT 配置保留原路径。

## 机制与限制

起播余量同时按串行/网络/争用条件验收。`stream_contended_startup_ms: 750` 与 `stream_contended_first_pcm_ms: 750` 在首个已证明 PCM 的实际请求耗时（容量等待+HTTP/模型/文本证明）达到 750ms 时，使用至少 750ms 起播余量，否则使用选定的低负载基础余量。独立诊断 flag 关闭时仍发送必要的第一块观测。候选在拿到第一块后才发布 `speech_start`，因此播放器在收包前收到实际选择值；失败且无PCM仍按有界重试/明确未完成提示处理，不能无限等首音频。该策略只增大余量、不更改音频或hold语义，是受控实测后的启发式，不保证任意网络/负载下不断流。后续还需用真实争用和公网一起检查，不能只看空载平均时延。

条件修复候选另有 `stream_contended_prebuffer_ms`（关闭为0）与 `stream_contended_prebuffer_wait_ms`（最大等待）。仅在首块请求达到候选阈值或普通容量已满/排队时，hold、输入守护和独立shift全部通过后，允许私下准备下一合成单元；实际备好音频达到目标才公开首播。短回复全部合成结束、两单元窗口已满或等待到期也会释放，避免为不可达到的目标产生新的依赖环。准备量按已暂存发送样本和有界交付队列估算，保守排除发送器当前一包。公开时重新唤醒信用等待，但不增加信用或已播样本。该候选不修改PCM或缓冲上限，是否进入默认配置由新的争用、串行和网络验收决定。

### 读取模型与等待播放分开

原来的 response 流在两个待合成句子占满后等待 TTS，同时继续持有普通请求许可；三个长回复可能占满三个普通槽，TTS 又等待这些槽。仅增加超时或容量不能消除这个依赖环。

`stream_text_read_ahead` 用独立可取消任务读取 response 源。它最多接受 16,384 个字符和 16,384 次源增量，包括空增量。模型源关闭后释放许可，后续分句仍按原队列容量交付。超出上限明确报错，不把截断输出作为完成；已经暴露的文字不重新生成/重播。任何消费端退出都会关闭源并等待读取任务结束。

同样，TTS 的上游请求不应因客户端暂未 ACK 播放而一直持有请求槽。`stream_pcm_read_ahead` 为单个 TTS 源设置 8 MiB / 4,096 块上限，源块仍受 512 KiB、PCM 对齐、固定有效采样率约束。完整读取后释放上游请求许可。这个缓冲与已有 2 秒交付预取队列不同：它按整个当前 TTS 源的硬预算读取，不能被描述成只增加 2 秒内存。最多当前和下一 TTS 单元进入既有管线；未确认候选的后续单元仍等待原确认门。客户端仍最多有 600ms 未确认播放音频，5 秒无信用进展明确失败。取消清理读取、合成和发送任务。

两个读取器不绕过生产 adapter 的逐字文本、正常文本终止、固定 speaker/请求 RNG 确认，也不裁剪 PCM 或改变 codec、MoE、native 数值设置。

显式候选 `stream_tts_source_prefetch` 将下一单元的上游读取和当前单元交付进一步分开。单会话仍只有一个活动上游TTS请求；前一源关闭后，可在当前音频仍等待信用时读取下一源。最多两个单元，各8MiB/4096块，实际播放交付队列仍为2秒、客户端信用仍为600ms。下一源仍等待已确认输入/独立shift门；未来源失败按交付FIFO排序，不丢弃已经排队的当前音频，也不标记成功完成。取消会关闭读取并清空私有源队列。该候选的验收记录独立于只增加起播余量的final/ready轨。

### 控制调度与第二轮

`input_control_reserve` 让 demo 的 `input_route` / `input_reply` 在播放开始前也进入保留的控制容量。总容量仍为 4，普通容量仍为 3；它不增加 GPU 调度序列数，也不保证任意人数/长度输入均能在两秒内完成。

`input_route_replaces_shift` 直接省去第二轮 shift 的候选未作为默认：真实带噪声第三方夹中，主路由会误接纳，而独立 shift 仍有正确拦截证据。不能因为它通常多花时间就称其完全冗余。

最终 `input_route_parallel_shift` 保留原独立音频 shift，按同一冻结快照同时准备私有 response。shift 尚未返回时，hold 确认也不能发布这份文字/PCM、写历史或启动 ASR；返回 no 才释放该候选。返回 yes 则取消并丢弃私有回答，执行原 shift_re 路径；异常/超时沿用原保守 fallback 语义。候选被替换、用户续说或停止时，两类请求一起取消。关闭并行 flag 恢复原串行 shift→response 路径。这个改动减少串行等待，会增加被拒绝候选的私有计算，必须在多人第二轮与取消竞态中另外验证。

### 首个可合成单元

`response_fast_first_sentence` 只在 demo 内追加独立提示：先给实质简短完整句，不为简单问题添加未请求的多个解释/例句；不能遗漏用户指定的故事、步骤或逐字朗读内容。单纯提示并不保证模型一定缩短首句，必须和真实生成及交付结果一起判断。

`stream_first_clause_chars: 8` 允许首个 TTS 单元在自然逗号处分开，中文至少约 8 字符，纯英文至少约 24 字符。数字分组、URL、引号和括号中的逗号受到保护；只影响第一单元，后续沿用原分句策略。重新连接各单元保持完整规范文本，不按字符阈值强行截断正文。短单元可能改变韵律，因此额外使用同文真实 TTS、离线 ASR 和未校准说话人嵌入诊断；这些不是 MOS 或身份验证准确率。

提前结束的逗号单元带有 `reply_complete: false`。已播放历史仍按实际 ACK 完成的 TTS 单元结算，但 `played-reply-v1` 不把它作为已播完完整问句：必须等后续单元结束并 ACK 到相应样本，才将拼接后的完整句纳入输入起点冻结的复核上下文。生成完成、发送完成或后来到来的 ACK 不回填输入起点快照。

### 有界分类尾部

`input_route_token_budget` 按本次实际路由音频总长度分配 `min(256, max(64, 48 + ceil(samples/1000)))` token，包括续说前文，不改变聊天生成预算。仅用于 demo 的音频分类与格式修复；`input_reply` 保持原预算。仍要求完整有序 transcript/label JSON 和合法标签，格式异常最多一次同音频修复，超时回 keep。这个经验预算只在受控配对验证通过后启用，不宣称所有真实语速/噪声下都无截断风险。

语法约束的实验接口 `input_route_grammar_mode` 支持 `off/repair/all`，生产选择 `"off"`。成对模型试验发现约束解码没有稳定改善延迟；把 512 字符展开为 counted EBNF 的方案尤其昂贵，已提前停止。YAML 的 `off` 必须加引号，避免被旧 YAML 布尔规则解析成 false。

### 因果计时

`DemoTrace` 通过 generation、input_id、parent_id 和 candidate_id 关联输入、候选、VAD、hold 与首音频，跨 epoch 的同一候选保持原输入锚点；显式未知 ID 不借用最近输入。三个关联表各最多 128 条，待首音频回复最多 64 条，旧 generation 首包不影响新回复。

开启文本读取器后，`speech_text_done.infer` 在真正 response 源关闭时停止，另外报告 `delivery_ms`。两者都包含 HTTP/消费开销，不能当作纯 GPU kernel 时间。模型请求、TTS 文本形成/证明/首块、页面首包/排程、完整播放与缓冲耗尽应分别读取；hold 与推理可以重叠，不可简单相加各阶段 P50。

## 验收口径

主链使用真实 VAD、Omni、Actor、WebSocket 和 Chromium WebAudio，输入来自已有自造 TTS/记录夹及 HumDial development 场景。GPU 实验进程串行，保持生产 seq4 内部重叠。首播指标在同一个浏览器时钟上用输入夹末到首次播放排程；活动末到可听声是 RMS 补充估计。它们不是物理麦克风/扬声器验收。

串行首播、FIFO 有序网络抖动、多人争用、明确停止、释放、故意丢播放信用、后来加入会话和真实 Windows→SSH 路径分别计数。故意信用故障不归入正常断流率；观察窗截尾保留首次结果并另做更长窗口的新试次，不把复测覆盖原失败。重复 seed/噪声/同根场景相关，不能当作独立真实用户或正式分类准确率。

原始案例、回复、音频、会话收据和诊断只在服务器私有实验目录保留。归仓收据只含机制、计数、聚合时延、断流、边界与部署事实。聚合实测收据归仓到 `exp/web_demo/latency_optimization_20261008/validation.json`；该收据记录最终默认参数、部署结果和拒绝的候选。私有明细报告仍在服务器实验目录。

## 争用识别和诊断配额

`stream_contended_source_stock` 在已有两单元硬预算内统计实际已验证并读取的 PCM，准备量是累计源样本减去已播样本；它可以观测超过两秒交付队列的库存，不把未来待生成音频计入准备量。目标最多五秒，仍只有当前/下一源各8MiB/4096块、两秒交付队列和600ms客户端信用。短回复全部源完成、两源窗口真正读完、目标达到或有界等待到期后才释放。四秒库存、最多4800ms等待是独立验收候选；并发首播更晚，换取已测多句回复的连续播放，不能宣称改善了原生TTS的持续吞吐。前文的1500ms仅交付库存候选失败后，才引入该模式；最终参数以聚合收据为准。

全源库存候选的私有准备期不启动客户端五秒无确认超时：客户端尚未收到这份音频，无法回传播放确认。私有信用等待另有最多十秒的硬界限（配置等待加五秒，上限十秒）；Actor公开 `speech_start` 后打开发布门，再开始原五秒信用等待。取消仍直接结束等待并收口子任务，不增加信用、不伪造播放进度，公开后断连仍明确失败。

`stream_contended_require_peer` 在启用时要求同一个 backend、同一请求容量对象下存在另一个尚未结束且未请求取消的 demo 语音管线，才允许触发争用起播/预缓冲。弱引用登记只作只读观察，不写其他Actor状态；自己的投机/替换管线、已结束及已取消管线不算其他用户。它不估计跨进程或绕过backend的GPU请求。单用户本身较慢的文本证明不能单独触发多人缓冲。旧的仅按首块400ms判断策略在空载发生误触发并显著变慢，原拒绝试次保留。

长期案例捕获仍有512MiB/2000条容量上限，不把trace完整等同于每个模型原始case都成功落盘。新发布配置使用独立 `exp/demo_cases_latency_20261008` 配额目录；旧实验/案例保留，不删除或覆盖。公开收据不包含原始case、转写或录音。

## 容量和候选筛选边界

四会话的回答完成与无断流是不同验收。最终250/300/350ms自适应起播，以及1500ms预备音频和提前读取下一TTS源的四会话候选，都出现缓冲耗尽；其原拒绝结果完整保留。现有总4/普通3容量、生产seq4不变，不能用增加一个有限缓冲来宣称四会话持续实时供给已经满足。

四会话拒绝后另行登记三会话计划，使用350ms基础起播、400ms首块阈值、750ms争用起播与1500ms预备音频，等待最多2500ms。它是新的明确场景范围，不能替换或洗掉四会话失败。三会话通过也仅说明该受控多句、第二轮和生命周期矩阵中的观测，不是并发用户数量承诺或新的线上会话准入限制。低负载与真实Windows路径必须另验收。

停止时间顺序提示在配对试验中改善“先请求后取消”，但导致一个原先正确的带噪声短请求退化，因此未进入默认。首播前控制容量可消除槽位等待，但不能消除模型的漏接或意图顺序判断错误。

## 验证与回退

针对性测试覆盖读取器容量/取消/错误顺序、真实队列下多人进度、迟来普通请求和控制槽、第一单元字符/引号/数字边界、完整句 ACK 复核、路由预算、因果计时、EOS/逐字/声音 adapter、历史与传输恢复。前端播放器另运行 `node tests/test_stream_demo.cjs`。

有独立GPU测试中途重启的一轮stock串行观测保留原始结果，但整体排除其延迟主表。新版本在每个试次前等待该任务结束，并以250ms采样检查整段试次是否重叠；出现重叠则发布门失败。该检查覆盖已识别的测试进程，不宣称检测了任意外部GPU使用。GPU实验内部仍保持生产seq4调度。

恢复原 demo 行为时关闭新增布尔 flag，将 `stream_first_clause_chars`、`stream_contended_startup_ms` 与 `stream_contended_prebuffer_ms` 设为 0，并恢复 `stream_startup_ms: 350`；`input_route_grammar_mode` 保持 `"off"`。通过正常 supervisor 启动链完整重启。现有 supervisor 发现 backend 子进程退出会关闭其全部子进程，包括 Omni，不能把杀掉 backend 当作独立热重载。
