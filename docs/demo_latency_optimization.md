# 单用户 Demo 延迟：四项问题的证据与状态

更新于 2026-10-08。目标是一个用户、一段会话中可能重叠的路由、回答、TTS、停止和取消调用，尽早开始实质回复并连续播放。请求槽数是内部调用准入限制，不是用户数。历史草案仅供审计：[归档入口](archive/demo_latency_scope_retired_20261008.md)。

**当前没有完美完整的解决方案。模型实验按用户要求保持停止。** 已确认工程已落实到源码和独立 Demo 配置，相关 CPU 回归 413 项通过、零失败/零跳过。未重启正式服务，运行进程仍需在下一次受控加载后验收；真实 Windows 接入和物理设备尚未验收。源码提交和配置启用不等于运行进程已加载新实现。

本次启用 `stream_text_read_ahead`、`stream_pcm_read_ahead`、`input_control_reserve`、`input_route_token_budget`、`input_route_parallel_shift` 和 `stream_first_clause_chars: 8`，均由独立 Demo 路径控制。350ms 起播、2000ms 交付预取、600ms 客户端信用、640ms 确认，以及原文本/EOS/声音校验保持。删除未采用的额外首句提示、路由 grammar、替代独立 shift 和动态起播实现分支。

本次还修复两个具体边界：上游源自行取消会在已接收内容之后交付明确失败，而不是让公开页面等待悬挂；旧代际的首音频/取消事件不会删除新回复的计时记录。正常消费者取消继续关闭源并等待任务退出。

验证收据：[413 项相关 CPU 回归](../exp/web_demo/latency_engineering_validation_20261008.json)。覆盖 18 个相关套件，其中新工程测试文件 88 项。验证是隔离环境的契约检查，没有模型调用，也没有新首播延迟测量。

## 1. 进度与控制：修复等待关系，区分语义错误

原 response 在两个待合成单元占满后等待 TTS，但继续持有普通请求许可；多个这种调用会使 TTS 等待许可。只改超时不能解除依赖环。文本读取候选在 16,384 字符/16,384 次增量的预算内独立排空源，关闭源后释放许可；交付仍有界，超限明确失败，已读内容先于后续错误交付。

PCM 读取候选为每个当前源设置 8MiB/4096 块预算，源块保持有效采样率、PCM 对齐和 512KiB 上限。源完成后释放许可，播放交付仍受原 2 秒队列、当前及下一单元、600ms 未确认播放信用约束。取消关闭源并等待读取任务退出。以上是释放源生命周期中的不必要占槽，不是放宽音频验证。

首播前控制预留候选维持 total=4、normal=3；它保证应用层准入关系，不抢占已运行的 GPU kernel。一条新的真实停止样本中，槽等待仅 2.4ms，分类仍耗时约 1.93s，并把先请求后停止的输入判成 yield_ready。这直接说明残留问题包括时序语义理解，不能继续全部归因于排队。

应保留上述结构修复，但不得宣称所有单用户场景已验收。未闭合的交错包括旧回答/TTS 与新输入重叠、首播前续说、不同阶段停止、撤销后马上重问、源异常及会话释放。回归可验证资源释放和发布屏障，不能替代这些真实交互。

## 2. 首播与播放：已有测量，尚缺实际接入

以下为历史候选组合的页面首播统计，其中包含本次未采用的额外首句提示；不能直接作为本次收敛提交版本的端到端实测收益。同轮核心条件的页面首播统计如下。起点是关联后的用户语音结束锚点；数值为该条件整体路径结果，不是只调整缓冲这一变量的因果收益。

| 条件 | 首播样本 | P50 ms | P95 ms | 回复完成 | 播放间隙 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线 | 14 | 1320.1 | 1477.8 | 14/14 | 0 |
| 350ms 候选组合 | 28 | 1218.8 | 1414.8 | 28/28 | 0 |
| 300ms 候选组合 | 28 | 1166.1 | 1372.5 | 28/28 | 0 |
| 250ms 候选组合 | 28 | 1117.0 | 1326.1 | 25/28 | 0 |

250ms 条件的三个原始 90 秒交付未完成记录保留；首播可观测不代表整段回复完成，不能把它们抹去，也不能仅凭这三条证明缓冲参数导致失败。另行预注册的延长截止重测是新尝试。

有序注入网络抖动，每条件 28 条：350ms 为 1494.3/1683.8ms（P50/P95）、全部完成且无间隙；300ms 为 1453.7/1829.9ms、全部完成且无间隙；250ms 为 1410.6/1763.7ms、全部完成但出现一次间隙。样本有限，不能断言 300ms 的真实尾部一定更差。

筛选结果：350ms 可作为保守的后续验收参照，300ms 保留比较价值；250ms 暂不选择。**本次保持既有 350ms 默认值，未持久化 300ms/250ms 调参，也未据历史延迟数字批准运行时验收。** Windows 经 SSH 的真实浏览器路径尚未运行，物理麦克风/扬声器体验也未验收。主线应同时看首播、断流、完整交付和听感，不能仅最小化首播中位数。

## 3. 首句与 TTS：首块改善不等于整体声音质量已证明

首个单元可在自然逗号处分开，中文约 8 字符、纯英文约 24 字符起；数字、URL、引号和括号受到保护，后续分句保持原策略，重新拼接保留完整规范文本。未形成完整语义句的首个逗号片段不会伪装成已播完整问句。逐字文本、正常 EOS 和声音/RNG 检查保留。

软提示单独没有稳定收益。组合测试的首文本→TTS 单元中位只改善约 8ms；TTS 请求→已证明首 PCM 中位改善约 101ms。后者同时包含容量、HTTP、模型和文本证明阶段，不能写成纯 GPU 加速，也不能把阶段中位差相加来解释端到端收益。

32 条同文真实 TTS（8 段自造文本×2 次重复×2 条件）全部通过功能/文本证明检查。首 PCM 中位约 423.7→350.2ms，但这是直接测试链路，不是实际浏览器首播。ASR 编辑数为基线 22/436、候选 20/436，不能当成人工可懂度评分。说话人嵌入仅提供未校准的描述性比较，不能证明跨文本声音完全稳定。

同文测试没有超过 5 秒的低能量片段，但另一交互样本出现约 36.5 秒低能量段。因此“传输没有断流”仍不能等价为“听起来没有长静音”。尚需判断首个实质回答何时形成、证明何时完成、后续 PCM 如何供给，以及自然分句是否改变韵律；当前没有裁剪音频来掩盖问题。

## 4. 分类与第二轮：保留正确性门，减少无效串行

路由预算的 512 对样本/1024 次决策来自 137 个根样本。观察标签变化 0，名义标签正确均为 439/512；两条件均无超时/回退，各修复 1 次。分类 P50 约 204.7→207.2ms，P95 273.0→268.2ms；最大值约 1895.3→732.6ms。结果支持控制特定冗长输出尾部，不支持普遍加速或解决语义漏判。原 2 秒总预算与失败保守 keep 仍在。

分类 grammar/条件修复候选没有稳定收益，未采用。时序提示虽在 176 对样本中使名义正确 149→157，并改善先请求后停止样本，却出现此前正确短问题退化，也未采用。收益不能覆盖已有正确行为的损失。

直接用 input_route 取代独立 shift 的候选被拒绝：带噪第三方样本中主路由误接纳，而独立 shift 正确拦截。保留独立音频判断，允许同一冻结快照的私有 response 同时准备；shift 通过前不发布文字/PCM、不写历史、不启动 ASR。否决时丢弃私有回答，取消时关闭双方。

每条件 4 条第二轮回复，350ms 候选 route→response 中位约 1.7ms，首播中位约 1428.5ms；基线分别 166.2ms、1518.4ms。消除约 164.5ms 串行派发等待，并没有自动换来等量首播收益。样本相关且少；真实连续修订和停止竞态尚未闭合，私有计算作废也要记录。

## 证据口径与下一步判断

此前候选相关回归 461 项通过；本次剔除未采用分支并补充边界测试后的相关回归为 413 项通过。这两组不能累加，不是独立产品成功次数。总浏览器记录 585 条含旧基线、重复尝试与其他条件，不能直接用其整体比例宣称单用户成功率；核心比较采用上表有效分母。原截止未完成记录保留，外部 GPU 重叠污染的延迟试验不进入有效比较。

保留进入下一步判断的机制：有界源读取/释放、控制预留、因果计时关联、首单元自然分句及完整句已播语义、输出预算、独立 shift 与私有回答并行。额外首句提示未纳入本次工程实现。保留 350ms/300ms 的实际接入比较，其他历史变体不作为当前待办或默认候选。

根本问题是允许重叠的工作被串行等待或下游交付不必要占槽阻塞，同时正确性仍依赖确认、音频分类和文本/声音证明。结构问题已有具体方案；模型时序语义、首句供给和真实播放质量仍有证据缺口。若用户以后明确恢复测试，应先闭合单用户取消/续说/停止/重问的真实状态交错，再验收实际接入，最后细拆首句证明与供块节奏。当前不执行这些测试。


## 剩余本质问题：只保留三项

停止慢、漏答、首播慢、长静音是用户可见现象，不能每个现象各立一个根因。按实际处理环节归并如下；未证实根因的子环节保持开放，不凭猜测指定修复。

| 优先顺序 | 本质问题 | 已有证据与未解决环节 | 下一步判断需要什么 |
| --- | --- | --- | --- |
| 1 | 输入接纳、最新意图判定与控制响应的可靠性 | 短语音仍可能因捕获边界、转写或分类被漏接；先请求后停止仍可能按旧请求回答。槽等待约 2.4ms 而分类约 1.93s 的案例说明排队修复不等于及时且正确停止。输出预算收敛特定尾部，但典型分类耗时未改善。 | 分开判读音频是否完整保留、转写是否忠实、最新意图是否正确、分类用时是否达标；目标是正确接纳请求、正确停止/等待/换题，并及时生效，同时保留第三方与含糊输入边界。 |
| 2 | 正确性约束下首个实质语音及后续音频的供给效率 | 队列和串行派发有工程改善，但首文本→可合成单元的历史改善仅约 8ms。首句内容形成、TTS 正常文本终止/证明、首块准备、后续供块尚未完全分离；真实接入的首播与连续交付还缺对应证据。 | 在同一因果计时链上定位关键路径，同时验收实质首播、完整交付和断流；不能通过说空承接句、取消文本证明或只降低缓冲来伪造收益。 |
| 3 | 合成音频本身的可听质量 | 另一个交互样本出现约 36.5 秒低能量片段；传输无断流不能证明没有合成静音。自然分句可能改变韵律，未校准嵌入和小样本 ASR 不足以证明声音一致和内容完整。 | 区分合成静音、供块停顿与实际播放间隙，检查可懂度、内容完整性、自然韵律和声音一致性；保留原音频证据，不剪音频掩盖问题。 |

单用户续说/停止/取消/重问交错、正式进程加载、真实 Windows/物理设备接入是上述工程和问题的验收条件。没有新故障证据时，不把“还需验收”另立为第四个优化问题。本次没有恢复模型实验或改动停止分类提示。
