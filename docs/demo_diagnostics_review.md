# Demo 诊断链审查与下一步优先级

日期：2026-09-21。范围仅包括 Phase-A ActorEngine 浏览器 demo 的逐轮 trace、实际模型调用案例库和离线声音诊断；不把 TACT/RB 冻结实验混入本审查。

## 1. 当前能力与本次只读审计

当前三条诊断线各自有效：

1. `demo-trace-v1` 用同一服务端单调钟记录 Actor 状态、候选、输入准入、容量、流式语音和浏览器数值遥测；服务端与浏览器时钟不直接相减。
2. `demo-case-v1` 保存实际送入模型的 payload、处理后音频、采样参数和调用输出，支持人工标签及串行单调用重放；观测结果不自动成为 gold。
3. 声音工具保存预声明比较清单，检查 PCM、ASR、F0、时长、请求级 RNG、Talker 中间状态和 LMFT speaker embedding；线上不使用未校准阈值。

本次仅聚合本机元数据，没有复制或展示会话文本/音频：54 个会话 trace 均有 `trace_closed`，`dropped=0`；案例库有 800 个实际调用，覆盖 35 个会话，其中 650 completed、148 cancelled、2 error。调用分布为 385 input_route、101 response、217 TTS、92 shift、3 shift_s、2 input_reply。只有 1 个案例存在人工 review。数字是此刻的本机快照，不是正式数据集规模或质量结论。

## 2. 最重要的缺口：没有可复现的完整轮次事故包

现在 trace、case 和声音产物是三个可关联但仍需人工拼接的岛：

- case 是单次模型调用，边界明确写着 `single-call`；它不知道调用结果最终是否被接纳、修复、判 stale、取消、公开、播放或写入历史。
- trace 有最终动作和播放事件，但没有统一 `call_id/span_id/parent_id`。同一种请求并发时，`capacity_acquired(kind=...)` 无法无歧义地对应某次 dispatch、case、模型完成或取消。
- trace 的 `session_start` 只有 trace 版本和 UTC；没有保存当次实际 engine overlay、prompt/协议版本、模型服务版本、Talker 模式、codec 分块和代码修订。旧案例保存了 payload，却不能完整回答“这轮状态机为何这样走”。
- 现有 replay 能复跑一个模型请求，不能复现输入帧时序、VAD 边界、640ms hold、候选确认、续说、播放 ACK、回压和迟到回调。

因此下一项工程不应是扩大无差别采集，而应生成一个**会话清单 + 轮次索引 + 可注入重放包**：

1. 会话开始保存脱敏的有效配置清单：代码修订、模型标识、各协议版本、engine flags、VAD/hold/容量/流式参数、Talker 模式、codec 分块、浏览器音频设置；不保存密钥或完整环境变量。
2. 每次 dispatch 分配稳定 `call_id`，所有 capacity/case/model done/repair/cancel/stale 事件携带它；使用 `parent_id` 连接输入、候选、回答、分句 TTS 和 utterance。
3. 每轮结束写一个机器可读 outcome：输入片段、原始模型标签、格式修复、最终路由、候选命运、回答 ID、公开/播放样本、历史写入和错误原因。
4. 支持用保存的帧时间、控制事件和模型输出做 Actor injected replay；模型单调用重放继续单列，不能把二者混称端到端复现。

这是当前诊断线的 P0，因为后面的自动归因、回归、标注抽样和版本比较都依赖它。

## 3. 第二个缺口：采集远多于标注，缺少异常优先队列

800 个调用只有 1 个 review，说明 CLI 的 `list → 手工找 case → label` 还没有形成可持续工作流。继续增加容量只会扩大未审数据堆积。

应增加本机 review 页面或终端 TUI，以“轮次”而不是“调用”为审查单位：

- 同屏显示处理后输入音频、路由转写/标签、最终动作、已播助手上下文、回答文本、TTS 音频和关键时序；默认不显示 base64 或无关底层字段。
- 支持问题类型多标签：VAD/截断、转写、路由、第三方/回声、回复内容、TTS 忠实度、音色、卡顿、取消、历史污染、无法判断。
- 标签记录 reviewer、时间、依据和修订历史；高风险项支持第二人复核，不静默覆盖首次判断。
- 分割以 session/说话人/源录音为组，避免同一真实输入的多个调用或变体跨 train/dev/test 泄漏。

优先队列不应随机展示所有 TTS，而应先抽取：

- repair/fallback/timeout/error；
- 模型调用完成但最终 stale/cancelled；
- stop/yield 后立即出现新输入或重新连接；
- 用户很快纠正、重复或再次要求停止的轮次；
- 高延迟、underrun、播放不足、旧包、history 改写；
- 新版本相对固定已审集发生标签变化的调用；
- 每类保留一部分随机样本，防止只看异常造成选择偏差。

页面可增加仅本机会话可见的“标记本轮有问题”按钮。它只记录轮次 ID 和可选问题类别，不发送自由文本到外部服务。

## 4. 第三个缺口：缺少自动 session invariant 审计

历史上多次故障都是用户看到异常后，再写专用脚本定位：感知冻结、候选泄漏、TTS 改写原文、参考文字被转写、短输入前截断、全局 RNG、并发 Talker 数值漂移、播放断流、打断标记进入回答。现有原始证据通常足够，但缺少每次会话自动执行的通用检查。

建议断线后生成私有 `session_summary.json`，至少检查：

- trace JSON 可解析、事件序号单调、`trace_closed.dropped=0`；
- started case 最终 queued，并能在案例库找到或明确记录写入失败；
- capacity 峰值不超过 total/normal 配置；
- 每个 input revision 最多产生一个最终接纳动作；
- stop_only/yield_wait 不产生无授权回答；
- 未确认候选不公开文本/音频、不写历史；
- cancel 后旧 utterance 不再发送或播放，播放样本不倒退且不超过 sent；
- stale generation/epoch/candidate 结果不改变状态；
- TTS 释放 PCM 前已有完整文本证明；
- assistant 模型历史只含允许的已播内容，不含内部控制说明；
- 每轮状态最终回到合法 LISTEN/SPEAK 状态，无遗留任务/容量票；
- 浏览器 underrun、socket slow send、模型修复/回退/超时按轮汇总。

检查器只判断机械不变量，不自动把语义模型输出判成正确答案。

## 5. 短停止问题仍缺采集前证据

案例库存的是“证据处理后实际送模型”的 WAV，不能回答音频在更早哪一层丢失：AudioWorklet、浏览器 AEC/降噪、重采样、网络包、服务端 deque、VAD 边界或声学过滤。现有历史已明确指出这一限制，却尚未实现有界采集。

如继续诊断短停止，优先增加显式 opt-in 的环形调试缓冲，而不是立即加停止词或第二 ASR：

- 只在受控调试会话启用；
- 保存 VAD 前后几秒的原始麦克风、渲染参考、重采样后输入、VAD 选段和最终模型输入；
- 所有轨道共享帧序号和样本钟，记录 AEC/降噪/AGC 实际设置；
- 本机私有、有容量和时间上限、自动过期，不进入 Git；
- 普通 demo 默认关闭，页面明确显示正在诊断采集。

这样才能区分“用户本来就没录清”“前辅音被 VAD/重采样丢弃”“回声门抑制”“Omni 已收到但识别错”。没有这组证据前，不应继续降低全局 VAD 阈值。

## 6. 模型与流式耗时仍缺统一请求级 span

当前 case `elapsed_ms` 可能包含播放信用和消费者回压，不能当纯模型 RTF；`capacity_acquired` 又没有请求 ID。建议为每个请求记录同一 `call_id` 下的：

- backend 容量等待；
- HTTP 建连/首响应；
- 首文本 token、文本结束；
- 首 PCM、末 PCM；
- 解码、PCM 队列等待、socket 等待、播放信用等待；
- cancel 发出、上游关闭确认；
- vLLM request ID 和可获得的 stage0/1/2 服务端时间。

每项必须注明时钟来源。浏览器和服务器可用带四个时间戳的 ping 估计时钟偏移和 RTT 区间，但仍不能宣称单向网络延迟或物理出声时间。

## 7. 声音诊断还缺“真实回答内的连续轨迹”与校准

现有声音评测善于回答固定文本重复、seed、动态批次和句长敏感性，但还不能回答用户最直接的问题：“一次真实多句回答听起来是否在句间换人或出现突变”。最有价值的下一步是：

1. 对实际回复按句子和固定滑窗提取 speaker embedding、F0、能量、语速、静音和波形边界指标，保留整句与局部轨迹。
2. 重点检查相邻分句，因为当前每句都是独立 TTS 请求；整段 embedding 可能平均掉一句异常。
3. 检查句间 click/DC 跳变、过长内部静音、模型内部停顿和播放 underrun，四者分开报告。
4. 构建有授权、长度匹配的同说话人正对和异说话人负对，用于理解分数范围；没有校准前继续禁止把 cosine 变成“换人概率”。
5. 固定一组短/中/长、中英混合、数字、问句、情绪变化文本，版本升级时成对复跑；继续保留逐句最差值，不只报聚合均值。
6. 产品展示前补少量盲听 ABX/MUSHRA 式人工评价，用来确认自动指标与“像不像同一个人/是否自然”的关系。自动指标不能代替主观听感。

这条线优先级低于端到端事故包和标注闭环，因为当前在线决策不依赖 speaker embedding；但它是下一步声音质量优化所必需的测量基础。

## 8. 版本漂移、容量与保留策略

建议增加只含聚合指标的本地健康报告：按版本统计 route 分布、repair/fallback/timeout、case drop、trace drop、取消率、underrun、首响分解、TTS 文本证明失败、声音逐句最差值和人工 review 覆盖率。用固定已审回归集比较新旧版本，差异小于供应方/样本噪声时不写成改善。

案例库当前达到配额后停止新增，且不自动删除。更广泛部署前应明确：

- 默认保留期和手动清理命令；
- 按 kind 分配配额，避免 TTS 大文件挤掉稀有控制失败；
- 异常全留、普通成功分层抽样；
- 会话删除能同时找到 trace、case、review 和派生报告；
- 任何导出默认脱敏，真实音频和文本不进入仓库。

## 9. 建议顺序

| 优先级 | 工作 | 直接收益 |
|---|---|---|
| P0 | 会话配置清单、统一 call/parent ID、轮次 outcome 索引 | 将 trace/case/播放真正连成因果链 |
| P0 | 端到端 injected session replay | 修复后可重放同一状态机，不再只复跑单请求 |
| P0 | session invariant 自动检查和异常优先队列 | 从事后人工翻日志变成自动发现机械错误 |
| P0 | 本地轮次 review UI/TUI、多轴标签 | 把已有800个调用转成可用回归资产 |
| P1 | opt-in 原始→处理后多轨环形采集 | 定位短停止究竟在哪一层丢失 |
| P1 | 请求级跨层 timing span | 分开容量、模型、回压、socket和播放等待 |
| P1 | 配额分层、采样、删除与保留策略 | 控制隐私和长期数据可用性 |
| P2 | 实际多句回答的逐句/滑窗声音轨迹与校准集 | 找句间换声、短句误判和局部异常 |
| P2 | 聚合健康趋势和版本对照报告 | 发现模型、配置和依赖升级造成的漂移 |

最小可交付顺序应是：先加统一 ID 与 session manifest，再写 post-session checker；随后用 checker 输出驱动 review 队列，最后才扩大原始音频和声音指标采集。反过来先采更多数据，会继续扩大未关联、未标注、难以复现的库存。
